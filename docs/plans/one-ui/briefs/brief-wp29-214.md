## WP2.14 Watchdog for default-on · executor · reviewer · [codex: PM rule above] · JS-only
**Why the WP0.4b watchdog is not enough for default-on** (`apps/mobile/lib/watchdog.ts`, 292 lines, so DON'T GROW IT; put new rules in `lib/watchdog-policy.ts`):
1. **The strike loop under the remote flag.** Strike 2 clears only the C4 override (`watchdog-gate.ts:55,98`) and owes `FALLBACK_LAUNCHES = 1` (`watchdog.ts:20,200`). After that launch `decideMount` resets strikes to 0 (`:96-109`) and retries the DOM. With remote `sharedUi:true` and a DOM that breaks on every launch, the cycle is DOM-fail, DOM-fail, native, and repeats: 2 of every 3 launches burn up to `READY_TIMEOUT_MS = 10_000` (`:18`) on a broken screen.
2. **The launch flag source is late and network-first.** `routeFlags` starts at `DEFAULT_ROUTE_FLAGS` (`sharedUi:false`, `routes.ts:128`; `App.tsx:234`). `useDomMount` only starts once `wantsDom` turns true (`watchdog-gate.ts:63-64`), which happens after `loadAppConfig` (network-first, 3 s timeout, then last-good; `app-config.ts:64-84`). At default-on, every launch therefore shows the native tree, then swaps to the DOM up to 3 s later. If WP5.1 instead flipped the compiled default to `true`, the DOM would start before any config arrived, and a remote kill switch could never stop it on that launch.
3. **No telemetry.** Strikes reach only `diagCollector` marks and the Diagnostics panel (`DiagnosticsPanel.tsx:116-117`). Nobody learns that a cohort is falling back.
4. **The `pending` flash** was deferred in WP0.4b (`PLAN.md:221`): the native tree renders while `mount==='pending'` (`App.tsx:381` renders the host only on `'dom'`).

**Do (one PR; split policy/gate if > 400):**
- **Flag resolution at launch (call):** `wantsDom = override || launchSharedUi`, where `launchSharedUi` = the **last-good cached** `sharedUi`, if present, else the compiled default. This is read before `decideMount` (one local file read through `readLastGood`; export a `loadLaunchFlags()` from `app-config.ts`, reusing it rather than duplicating). The network result is cached as today and applies on the **next** launch; there is still no live unmount. That makes the kill switch "set `sharedUi:false` in `config/mobile/app-config.json` → publish (docs/mobile-release.md:285-290) → effective on each device's second launch after publish". Document that latency. WP5.1 then flips **both** the JSON and `DEFAULT_ROUTE_FLAGS.sharedUi` (so an App Review fresh install sees the shared UI), and the cache wins over the default once fetched. Add a test pinning that order: override > cache > default.
- **Quarantine (strike policy):** add `fallbackCycles` to the record (`v:2`; `parseRecord` upgrades `v:1` with `fallbackCycles:0`; a malformed record = fresh, as today). Strike 2 → fallback as today. When `fallbackCycles` reaches `QUARANTINE_AFTER = 2` within one `buildKey`, the state is `quarantined`: native for every launch until the `buildKey` changes (new OTA or binary, `watchdog-store.ts:11-13`) or the Diagnostics "Reset watchdog" button. A ready launch resets `fallbackCycles`. Worst case per bad build: 2 failed DOM attempts, then native, then 2 more failed attempts, then native forever. The C4 override clear stays as is.
- **Gate timing:** `READY_TIMEOUT_MS` stays a constant. 2.14 sets it to `max(10 s, 2 × S7 p95 time-to-ready on the slowest device)` and records the number and source in the PR. If S7 hasn't happened yet, keep 10 s and file the follow-up in PROGRESS.

Diagnostics gains "Reset watchdog" (calls `clearWatchdogRecord`, `watchdog-store.ts:34`) and shows `fallbackCycles`/`quarantined`.
